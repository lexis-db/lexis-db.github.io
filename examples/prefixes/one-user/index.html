Motivation

Records that belong to a parent are a common pattern: a user's orders, a tenant's documents, a device's readings. Key them by the parent's id and then their own, with both as the partition key, and every record is its own partition. For example, user_orders keyed by (user_id, order_id), with each user's newest orders first.

In ScyllaDB the token is a hash of the whole key, so only a complete key can be looked up efficiently. Listing a user's orders, paging through them, or ranging over users all name just the start of the key, and ScyllaDB rejects them:

Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING

or, for a range on part of the key:

Only EQ and IN relation are supported on the partition key (unless you use the token() function or allow filtering)

With ALLOW FILTERING they run as full scans of every node and return rows in hash order. The usual workarounds are a secondary index, a second table keyed for each access pattern, or moving order_id into a clustering column, which puts all of a user's orders into one partition that cannot be split.

In Lexis the token is the key itself, encoded so that byte order is key order. Keys that share a prefix are stored together, so each of these patterns becomes a read of one contiguous range of tablets, in key order, without ALLOW FILTERING.

Partition key order

Partitions are stored, distributed and returned in key order, and Lexis adds PARTITION ORDER BY to choose that order.

ASC or DESC per column

Each partition key column can be declared ASC or DESC, as CLUSTERING ORDER BY does for clustering columns. The direction is fixed when the table is created, ASC is the default, and directions can be mixed.

cqlsh:lexis
>CREATE TABLE user_orders (user_id text, order_id text, item text, PRIMARY KEY ((user_id, order_id))) WITH PARTITION ORDER BY (user_id ASC, order_id DESC);
CREATE TABLE user_orders (user_id text, order_id text, item text, PRIMARY KEY ((user_id, order_id))) WITH PARTITION ORDER BY (user_id ASC, order_id DESC);

Types

The token encodes each column in its direction: an ASC column as order-preserving bytes, a DESC column as their complement, so its largest value comes first. Every scalar key type sorts as CQL compares it, in either direction and with every range operator; text and blobs sort lexicographically.

Tokens

The token is the key, so you can read it.

token() is a blob

token() returns the encoded key: each component's bytes, then 00 00. A DESC component is the complement, ending in ff ff. Here that is u42, then o100.

cqlsh:lexis
>SELECT user_id, order_id, token(user_id, order_id) FROM user_orders WHERE user_id = 'u42' AND order_id = 'o100';
user_idorder_idsystem.token(user_id, order_id)
u42o1000x753432000090cecfcfffff
(1 row)
SELECT user_id, order_id, token(user_id, order_id) FROM user_orders WHERE user_id = 'u42' AND order_id = 'o100'; --- user_id | order_id | system.token(user_id, order_id) ---------+----------+--------------------------------- u42 | o100 | 0x753432000090cecfcfffff

Bind markers

Prepared, and routed by the drivers

Every query above can be prepared. The Lexis drivers compute the same token range as the server and send the statement to the replica and shard that hold it: a full key goes straight to its partition, and a prefix, or a prefix ending in a range, goes to the tablet where its range starts, which for most prefixes is the only one.

app.py
q = session.prepare("SELECT * FROM user_orders WHERE user_id = ?"
                    " AND order_id < ? LIMIT 2")
session.execute(q, ('u42', 'o101'))
q = session.prepare("SELECT * FROM user_orders WHERE user_id = ?" " AND order_id < ? LIMIT 2") session.execute(q, ('u42', 'o101'))

Queries that still need ALLOW FILTERING

No user named

cqlsh:lexis
>SELECT * FROM user_orders WHERE order_id = 'o100';
SELECT * FROM user_orders WHERE order_id = 'o100';
 
Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING

With ALLOW FILTERING this scans the whole table.

A column after a range

cqlsh:lexis
>SELECT * FROM user_orders WHERE user_id > 'u1' AND order_id = 'o5';
SELECT * FROM user_orders WHERE user_id > 'u1' AND order_id = 'o5';
 
Only EQ and IN relation are supported on the partition key (unless you use the token() function or ALLOW FILTERING)

With ALLOW FILTERING this reads only the users after 'u1' and filters them.

cqlsh:lexis filtered
>SELECT * FROM user_orders WHERE user_id > 'u1' AND order_id = 'o5' ALLOW FILTERING;
user_idorder_iditem
u7o5pen
(1 row)
